# InfoMancer 0.8 alpha performance pass

This document records the optimization work applied to `testing/0.8-alpha` and the invariants the implementation is intended to preserve.

## Request and asset path

- Static asset cache versions are content-derived instead of process-time-derived, so unchanged CSS and JavaScript remain cacheable across application restarts.
- Versioned static assets retain immutable browser caching.
- Large HTML, CSS, and JavaScript responses are gzip-compressed.
- The account avatar has one client-side network owner, uses a stable URL, and revalidates with ETags rather than cache-busting every page load.
- Independent global workspace controllers start in parallel. Ordered Library controllers begin fetching together while preserving execution order.
- The task widget reuses the base task poll when available and skips DOM rebuilds when the task set is unchanged.

## Library hot path

- Default `/library`, `/movies`, and `/shows` landings select at most 1,000 visible candidate titles before computing file and missing-episode aggregates.
- Common free-text search collects, sorts, filters, and caps candidate title IDs before file/missing-episode aggregation.
- Fuzzy person matching is fallback-only. Direct title, filename, tag, and credit matches do not pay for the fuzzy scan.
- Live search uses `library_results.html`, a result-only template, and bypasses global page context processors plus unrelated option/saved-view queries.
- Advanced filter combinations continue to use the mature Library handler, but live requests strip the response down to the cover and list result surfaces.
- List and Covers share one full server render cache entry. The active surface is sliced from that source in memory, so changing views does not repeat the expensive query/Jinja render.
- Library hover/focus/idle warming populates the server render cache but returns HTTP 204 with no discarded page body.
- Render-cache revision checks use one SQLite statement instead of a sequence of independent revision queries.

## SQLite and global chrome

- Read-path indexes cover Library revision checks, title tags, expected-episode lookups, episode file ranges, activity reads, and due-announcement reads.
- `AppSettings` keeps a thread-safe process-local snapshot and invalidates it after writes.
- The template engagement state coalesces tour/setup/announcement reads into one short-lived per-user snapshot during a page render.
- Official announcement seeding avoids rewriting unchanged rows, preventing restart-only timestamp churn and needless cache invalidation.
- The global unread-activity badge uses a count-only SQL query instead of loading and JSON-decoding up to 250 activity rows.
- Event-log retention cleanup is amortized to every 128 inserted events instead of running a 50,000-row retention query after every log write.

## Deliberately deferred structural work

`app/static/library.css` and `app/main.py` remain large. Splitting them is primarily a maintainability refactor, not an automatic runtime win. During active 0.8 alpha UI testing, blindly moving cross-surface CSS or route families would create a much larger regression surface than the measured hot-path work above. The safer follow-up is an ownership audit followed by small extraction PRs with visual/route contract coverage.

## Validation

For local validation run:

```bash
python -m unittest discover -s tests -v
python -m compileall -q app
python scripts/benchmark_library.py
```

Benchmark numbers should be reported from the same machine and synthetic library size before and after a change. This pass intentionally records structural improvements rather than claiming a percentage speedup without comparable benchmark measurements.
